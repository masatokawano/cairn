# orchestration.md — マルチモデル運用規約（Fable / Opus / Sonnet / Codex）

- 作成日: 2026-07-03
- 位置づけ: AGENTS.md の「モデル / エージェントの役割」の詳細。**「何を作るか」は
  docs/DESIGN.md が正**であり、本文書は「誰が・どの設定で・どう引き継ぐか」のみを定める。
  DESIGN.md / AGENTS.md と矛盾したらそちらが正。
- 読むタイミング: セッション開始時のモデル選定、実装→レビューのハンドオフ、
  レビュー結果の反映時。通常の実装作業中に読む必要はない。

## 1. モデル特性と選定基準

### Claude Fable 5

- 用途: マイルストーン実装セッションの既定モデル。計画承認後の長い自律実行に最も適する。
- effort 設定:
  - **high（既定）**: M0〜M6 の通常実装。
  - **xhigh**: 不可逆かつ設計難度の高い作業のみ。本リポジトリで該当するのは
    (a) chunks → items 参照化の migration 設計（M0）、
    (b) 検索基盤の items 一般化の設計判断（M2）、
    (c) MCP の provenance 分離レスポンス設計（M5）程度。実装フェーズは high に戻す。
  - **medium/low**: 使わない（その規模のタスクは Sonnet に回す方が安い）。
- 既知の注意点:
  - 高 effort では依頼範囲外の調査・リファクタに踏み出しやすい。AGENTS.md の
    「スコープと報告の規律」を計画承認時に再掲すると効く。
  - **安全分類器の過検知**: 本リポジトリには redaction・シークレット検出・
    インジェクション対策コードが含まれ、これらを扱うプロンプトで Fable が
    拒否・回避的応答をすることがある。2 回言い換えても解けない場合は
    そのタスクだけ Opus 4.8 に切り替える（下記）。無理に迂回表現を探さない。

### Claude Opus 4.8

- 用途:
  1. **セキュリティ関連コードの実装・レビュー**: `redact` 系、obsidian_writer の
     allowlist / パス検証、MCP のガード指示と provenance 分離、Keychain ヘルパ。
     防御コードの意図を攻撃者視点で検証する作業はここに含む。
  2. **Fable の分類器過検知時の fallback**（タスク単位で切替、セッション全体を移す必要はない）。
  3. 設計相談・Decision Record 改訂案の壁打ち。

### Claude Sonnet 5（effort: high 相当）

- 用途: docs/backlog.md の XS/S タスク（backup ローテーション、httpx warning 解消、
  temp/ 整理等）、README/文書更新、`npm run build` を伴う軽微な UI 修正、
  テスト fixture 追加。
- 判断基準: 「変更ファイル 1〜3 個・schema/API 変更なし・不変条件に触れない」なら Sonnet。
  それを超えたら Fable に回す。Sonnet のセッション中にこの基準を超えると判明したら、
  実装を続けず報告して終了する。

### Codex CLI

- 用途: **独立レビュー専任**。実装した系統（Anthropic モデル）と別系統であることが価値。
  実装には原則使わない（過去の CODEX_PROMPT 時代の「Codex が実装方針を書く」運用は
  docs/history/ に退避済みの歴史的経緯であり、現行は本文書が正）。
- レビュー対象: 各マイルストーン完了時の diff。特に M0（migration）、M3（書き込み
  allowlist）、M5（MCP）は必須。M4 の週次レビュー生成のような低リスク変更は任意。
- Codex は AGENTS.md を自動で読む。レビュー依頼時は §4 のテンプレートを渡す。

## 3. セッション運用パターン

### 3.1 実装セッション（Fable / Sonnet）

1. AGENTS.md（自動読込）→ DESIGN.md §2・§8 → NOTES.md の順で読む。
2. 対象マイルストーンの目的を S1〜S5 に紐づけて 1 行で確認（AGENTS.md 作業手順）。
3. 実装計画を提示 → 人間が承認。
4. 承認範囲内は自律実行。不可逆操作（不変条件 8）のみ都度確認。
5. 完了報告（§4.1 の様式）+ NOTES.md への教訓追記（あれば）。
6. commit はローカルまで。push は人間の明示指示。

### 3.2 レビューセッション（Codex）

1. §4.2 の依頼テンプレートを受け取る。
2. AGENTS.md 末尾のレビュー観点で diff を検査。
3. 指摘は §4.3 の様式で返す。**指摘 = 修正ではない**。Codex はコードを変更しない。

### 3.3 レビュー反映と往復上限

- 指摘の反映は元の実装モデル（通常 Fable）が行う。反映後に再レビュー。
- **往復は 2 周まで**。2 周で収束しない指摘は、モデル同士で解決させず人間が裁定する
  （設計上の見解相違である可能性が高く、必要なら Decision Record 改訂として扱う）。
- 指摘への反映で新たなスコープ拡大をしない。指摘外の「ついで修正」は禁止。

## 4. ハンドオフ様式

### 4.1 実装完了報告（実装モデル → 人間 / レビュアー）

```markdown
## M<N> 実装報告（<日付> / <モデル名・effort>）
- 対象: DESIGN.md §7 M<N> のうち <範囲>
- 変更ファイル: <一覧>
- schema/API 変更: <なし / 内容。migration 版数と premigrate バックアップの確認結果>
- テスト: <コマンド> → <passed 件数>（ベースライン <件数> からの増減と理由）
- 完了条件の充足: <DESIGN.md の完了条件を引用し、それを検証するテスト名を対応づけ>
- 未解決 / 報告事項: <範囲外で気づいた問題。修正はしていない>
- 次の推奨タスク: <1 行>
```

### 4.2 レビュー依頼（人間 → Codex）

```text
Cairn の M<N> 実装レビューを依頼する。実装は Claude (<モデル>) が行った。
まず AGENTS.md と docs/DESIGN.md §2・§8、続いて以下を読むこと。
- 対象 diff: <コミット範囲 or ブランチ>
- 実装報告: <4.1 の報告を貼る>
AGENTS.md 末尾の「レビュー観点」7 項目に沿って検査し、指摘ごとに
[blocker/should/nit] を付けて報告せよ。コードは修正しないこと。
特に確認: <そのマイルストーン固有の重点。例: M0 なら「migration が冪等か、
既存検索の回帰テストが実際に旧挙動を検証しているか」>
```

### 4.3 レビュー報告（Codex → 人間）

```markdown
## M<N> レビュー報告（Codex / <日付>）
- 総評: <承認可 / 条件付き / blocker あり>
- 指摘:
  - [blocker] <ファイル:行> <内容と根拠（不変条件 N / DESIGN.md §X）>
  - [should] ...
  - [nit] ...
- 実装報告との突合: <報告された内容と diff・テスト結果の不一致があれば記載>
```

## 5. エスカレーション規則（全モデル共通）

- 同一の失敗が 2 回続いたら試行をやめて報告（AGENTS.md 作業手順と同じ）。
- 不変条件・§8 非目標と衝突する必要性に気づいたら、実装せず Decision Record 改訂案として報告。
- Fable の安全分類器過検知は 2 回の言い換えまで。それで解けなければ Opus へタスク切替。
- モデル間で見解が割れたら人間が裁定（§3.3）。モデルの多数決はしない。

## 6. 本文書の保守

- モデルの世代交代・effort 体系の変更時は本文書の §1〜§2 のみ更新すればよい
  （AGENTS.md 側は要約表の差し替えのみ）。
- 「どのモデルが何をしたか」の実績は本文書に書かない。commit メッセージと
  §4.1 報告に残る。
