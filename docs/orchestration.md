## 1. モデル特性と選定基準

モデル世代が交代したら「現在: ◯◯」の箇所だけ差し替える。役割の定義は変えない。

### 実装既定モデル（現在: Claude Opus 4.8）

- 用途: マイルストーン級の実装セッション。計画承認後の長い自律実行。
  **セキュリティ関連コード**（`redact` 系、obsidian_writer の allowlist / パス検証、
  MCP のガード指示と provenance 分離、Keychain ヘルパ）もここが担う
  （旧規約では Fable 5 が実装既定・Opus がセキュリティ専任だったが、Fable 退役に伴い統合）。
- 設計相談・Decision Record 改訂案の壁打ちもここ。
- **不可逆かつ設計難度の高い作業**（migration 設計、全経路が通る関数の変更、
  データ完全性に関わる変更）は、最高 effort に上げるだけでなく、**実装前に独立の
  Plan/Review エージェントを 1 本挟む**（memory: feedback-opus-review-for-migrations の
  運用を標準とする。実装後レビューの代替ではなく前段の追加）。
- 既知の注意点: 高 effort では依頼範囲外の調査・リファクタに踏み出しやすい。
  計画承認時に AGENTS.md「スコープと報告の規律」を再掲すると効く。

### Claude Sonnet 5（effort: high 相当）

- 用途: docs/backlog.md の XS/S タスク（backup ローテーション、httpx warning 解消、
  temp/ 整理等）、README/文書更新、`npm run build` を伴う軽微な UI 修正、
  テスト fixture 追加。
- 判断基準: 「変更ファイル 1〜3 個・schema/API 変更なし・不変条件に触れない」なら Sonnet。
  それを超えたら実装既定モデルに回す。Sonnet のセッション中にこの基準を超えると
  判明したら、実装を続けず報告して終了する。
- Sonnet には §2 実行規律のうち特に G2（完了ゲート）と G4（スコープ既定）を
  依頼文に明示的に貼る（暗黙遵守を期待しない）。

### Codex CLI

- 用途: **独立レビュー専任**。実装した系統（Anthropic モデル）と別系統であることが価値。
  実装には原則使わない（過去の CODEX_PROMPT 時代の「Codex が実装方針を書く」運用は
  docs/history/ に退避済みの歴史的経緯であり、現行は本文書が正）。
- レビュー対象: マイルストーン級の diff は必須（M0〜M6 では migration・書き込み
  allowlist・MCP を必須とした実績）。低リスク変更は任意。
- Codex は AGENTS.md を自動で読む。レビュー依頼時は §4 のテンプレートを渡す。

## 2. 実行規律（旧既定モデルの作業スタイルの手順化。全実装モデル必須）

旧実装既定（Claude Fable 5、〜2026-07）が暗黙に守っていた進め方を、モデルの地力に
依存せず再現できるようゲート化したもの。**各ゲートは「守れたか」を yes/no で
点検できる形になっている。完了報告の前に G1〜G6 を自己点検すること。**

- **G1 実測ゲート**: 報告・文書・コミットメッセージに載せる数値・パス・版数・件数は、
  **同一セッションのツール出力**を根拠とする。既存文書の記述は実測するまで仮説として
  扱う（例: schema 版数は `PRAGMA user_version`、テスト数は pytest の出力行、
  参照先の実在は ls で確認してから broken と判定）。安く再実測できるものは再実測する。
- **G2 完了ゲート（definition of done）**: 次の 4 段をすべて通ってから「完了」と書く。
  ① テストが pass した**出力**を確認 → ② 実データ / 実環境で DESIGN.md の完了条件を確認
  → ③ 文書追従: ROADMAP.md の状態表・docs/backlog.md・memory の該当行を**同じセッション
  で**実態に合わせる → ④ §4.1 様式で報告。1 段でも欠けたら「未完了 + 残作業」として
  報告する（欠けたまま完了と書かない）。
- **G3 継続規律**: 「次に〜します」と書いたら、そのターンで実際にツールを呼ぶ。
  計画・宣言・選択肢の列挙・質問で自分のターンを終えない（例外は不変条件 8 の
  承認待ちと、ユーザーにしか出せない情報のみ）。同一の失敗が 2 回続いたら
  3 回目を試さず停止して報告する。
- **G4 スコープ既定（迷ったときのデフォルト）**: 依頼範囲外の問題は**直さず報告に載せる**
  （報告 = 修正許可ではない）。操作の危険度分類に迷ったら常に安全側（承認を要する側）へ。
  文書と実装が矛盾したら、実装ではなく文書修正の提案が先。
- **G5 高リスク変更の検証パス**: migration・一括変更・大量ファイル操作では、
  ① 着手前に Before State を記録（repo の HEAD と対象範囲の `git status`、git 管理外は
  checksum）② git 管理外ファイルは編集**前**にバックアップ ③ コミットは対象ファイルのみ
  選択ステージ ④ 完了時に「自分が何をしたかの記憶」ではなく**外部証跡**（diff・checksum・
  テスト出力）で自分の変更一覧と突合し、不一致は直さずそのまま報告する。
- **G6 アンカー再読**: `deliver/` 配下・migration・MCP ガード・redaction に触れる**直前**に
  AGENTS.md の不変条件と DESIGN.md §8 を読み直す（長いセッションでの制約忘れ対策。
  「読んだはず」を根拠にしない）。

## 4. セッション運用パターン

### 4.1 実装セッション（実装既定モデル / Sonnet）

1. AGENTS.md（自動読込）→ **本文書 §2 実行規律** → DESIGN.md §2・§8 → NOTES.md の順で読む。
2. 対象タスクの目的を S1〜S5 に紐づけて 1 行で確認（AGENTS.md 作業手順）。
3. 実装計画を提示 → 人間が承認。
4. 承認範囲内は自律実行（G3）。不可逆操作（不変条件 8）のみ都度確認。
5. 完了は G2 の 4 段を通してから報告（§5.1 の様式）+ NOTES.md への教訓追記（あれば）。
6. commit はローカルまで。push は人間の明示指示。

### 4.2 レビューセッション（Codex）

1. §5.2 の依頼テンプレートを受け取る。
2. AGENTS.md 末尾のレビュー観点で diff を検査。
3. 指摘は §5.3 の様式で返す。**指摘 = 修正ではない**。Codex はコードを変更しない。

### 4.3 レビュー反映と往復上限

- 指摘の反映は元の実装モデルが行う。反映後に再レビュー。
- **往復は 2 周まで**。2 周で収束しない指摘は、モデル同士で解決させず人間が裁定する
  （設計上の見解相違である可能性が高く、必要なら Decision Record 改訂として扱う）。
- 指摘への反映で新たなスコープ拡大をしない。指摘外の「ついで修正」は禁止。

## 5. ハンドオフ様式

### 5.1 実装完了報告（実装モデル → 人間 / レビュアー）

```markdown
## <タスク名> 実装報告（<日付> / <モデル名・effort>）
- 対象: <DESIGN.md §7 / backlog / status doc の該当項目>
- 変更ファイル: <一覧>
- schema/API 変更: <なし / 内容。migration 版数と premigrate バックアップの確認結果>
- テスト: <コマンド> → <passed 件数>（ベースライン <件数> からの増減と理由）
- 完了条件の充足: <完了条件を引用し、それを検証するテスト名 / 実測結果を対応づけ>
- 実行規律の自己点検: G1〜G6 の各 yes/no（no があれば理由）
- 未解決 / 報告事項: <範囲外で気づいた問題。修正はしていない>
- 次の推奨タスク: <1 行>
```

### 5.2 レビュー依頼（人間 → Codex）

```text
Cairn の <タスク名> 実装レビューを依頼する。実装は Claude (<モデル>) が行った。
まず AGENTS.md と docs/DESIGN.md §2・§8、続いて以下を読むこと。
- 対象 diff: <コミット範囲 or ブランチ>
- 実装報告: <5.1 の報告を貼る>
AGENTS.md 末尾の「レビュー観点」に沿って検査し、指摘ごとに
[blocker/should/nit] を付けて報告せよ。コードは修正しないこと。
特に確認: <そのタスク固有の重点。例: migration なら「冪等か、
既存検索の回帰テストが実際に旧挙動を検証しているか」>
```

### 5.3 レビュー報告（Codex → 人間）

```markdown
## <タスク名> レビュー報告（Codex / <日付>）
- 総評: <承認可 / 条件付き / blocker あり>
- 指摘:
  - [blocker] <ファイル:行> <内容と根拠（不変条件 N / DESIGN.md §X）>
  - [should] ...
  - [nit] ...
- 実装報告との突合: <報告された内容と diff・テスト結果の不一致があれば記載>
```

## 6. エスカレーション規則（全モデル共通）

- 同一の失敗が 2 回続いたら試行をやめて報告（G3）。
- 不変条件・§8 非目標と衝突する必要性に気づいたら、実装せず Decision Record 改訂案として報告。
- 実装モデルが安全分類器の過検知（redaction・インジェクション対策コード等を扱う
  プロンプトでの拒否・回避的応答）を起こしたら、言い換えは 2 回まで。解けなければ
  タスクを分割するか人間へ報告する。無理に迂回表現を探さない。
- モデル間で見解が割れたら人間が裁定（§4.3）。モデルの多数決はしない。

## 7. 本文書の保守

- モデルの世代交代・effort 体系の変更時は §1 の「現在: ◯◯」と §3 のみ更新すればよい
  （AGENTS.md 側は要約表の差し替えのみ）。**§2 実行規律はモデル非依存であり、
  世代交代で書き換えない**（変えたくなったら、それは規律の改訂 = 人間の承認事項）。
- 「どのモデルが何をしたか」の実績は本文書に書かない。commit メッセージと
  §5.1 報告に残る。
