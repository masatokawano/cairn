## 3. 目的適合性の分析（DESIGN.md §1 との照合）

### 3.1 目的への適合

目的:「保存するだけでなく**自動的に記憶し、必要な時・意外な時にいい感じに思い出させる**。
日常行動は変えない」。

アーキテクチャはこの目的に忠実に着地している。pull 経路（週次レビュー）と push 経路
（MCP コンテキスト注入）の両方が実装され、原本非複製・read-only・派生データ再構築可能の
原則も保たれている。「日常行動を変えない」も、取り込みは launchd 自動化 + 既存習慣
（Karakeep 保存・Zotero 保存）のままで成立している。

ただし**目的の前提とデータの現実に 2 つの乖離**がある（実装バグではなく運用ギャップ）:

1. **「着想を書く → Obsidian Inbox」の習慣が現状存在しない**。索引対象 4 ディレクトリ
   （10 Themes / 20 Projects / 00 Inbox/Ideas / 50 Decisions）は全て空で、4 系統のうち
   「理解」の脚が欠けている。S5 の「構想」バケットが会話のみで構成される。
2. **Gemini 会話が本番 DB に 0 件**。4+1 ソースのうち 1 経路が未接続のまま。

### 3.2 成功基準 S1〜S5 の現状評価

| # | 基準 | 現状評価 |
|---|------|---------|
| S1 | 週次レビュー 10 分以内 | **構造的に担保**（各節 ≤10 件、D6）。W28 実物 6.6KB は読了可能な分量。読了時間の実測は M6③ |
| S2 | 週 1 件以上の再発見 | 機構は稼働（W27/W28 に「過去からの関連」が理由付きで出力）。**主観評価は M6③**。semantic アームのノイズ混入あり（R5） |

| S4 | ゼロメンテ運用 | 失敗通知実装済み・稼働以来失敗ゼロ。**穴 2 つ**: 手動エクスポート鮮度（設計上の既知、陳腐化警告で緩和）と embedding バックログ（R3） |

### R2: M6③ 実運用評価の実施設計（〜2026-07 下旬、W29〜W31）

毎週日曜のレビュー到着後に 5 分で記録する（記録場所は Obsidian の任意ノートでよい。
週次レビューファイル自体への評価欄追加は §5.4 の書式改訂になるため M6③ 中はしない）:

1. S1: レビュー読了に要した分数。
2. S2: 「過去からの関連」に実際に忘れていた項目があったか（○/×、あれば 1 行メモ）。
3. S2 副次: 明白なノイズ項目の件数（チューニングの入力になる）。
4. S3: その週に MCP（search_all / build_context_pack）を使った回数の概算。
5. S4: `failures.log` の有無と `sync_state.last_error` の確認（コマンド 1 本）。

3 週後に S1〜S5 を判定し、調整は**件数上限と related チューニングのみ**（§7 M6 の規定どおり）。

### R3: embedding バックログの定常処理（設計提案）

- 現状: 毎時 `sync all` は新規 chunk の embedding を行わないため、未埋め込みが 2,938 chunk
  （全体の約 9%）。M6 で実測した `cairn index rebuild` は本番コピーに対してであり、
  本番 DB へは未実行。**最近取り込んだ内容ほど semantic / hybrid 検索に載っていない**。
- 設計案: launchd に `com.masato.cairn.reindex`（深夜 1 回 `cairn index rebuild`、実測 ~60 秒）
  を追加する。これは D2 が禁じた「バッチ事前抽出」でも「恒常自動 embed のパイプライン化」
  でもなく、既存の再構築コマンドの定期実行である。ただし §5.7 の「エージェントは 2 本に
  集約」と字面上食い違うため、**先に DESIGN.md §5.7 の 1 行改訂を提案**する（文書が正の
  原則）。plist の load は不変条件 8 の承認事項。
- 暫定運用: 改訂までは export 取り込み後に手動で `cairn index rebuild` を 1 回実行する。

### R4: build_context_pack の evidence バケット精度（M6③ チューニング範囲)

- 症状: kind 別検索で代表性を保証する設計（NOTES.md M5 節の意図的判断）の裏面として、
  該当ブックマーク・文献が存在しないテーマでも低適合の top-k で埋まる
  （本日「SQLite FTS5 日本語検索」で実測: evidence 6 件が全て無関係の Karakeep 項目）。
- 設計案: バケット内の相対スコア閾値（先頭スコアの一定比率未満を落とす）を導入し、
  埋まらない場合は空バケットを許容して counts に正直に反映する。「該当なし」は
  受け手の LLM にとって有用な情報であり、無理に埋めるより S5 に資する。

### R5: related() の semantic ノイズ（M6③ チューニング範囲）

- 症状: semantic アームが無関係の長文ログ会話（OS インストールログ等）を拾うことがある。
- 設計案: (a) semantic 側にも距離閾値を導入、(b) `_is_noise_conversation` のタイトル規則を
  評価期間中の実ノイズで拡充。keyword アームの `_content_terms` は M4 で対処済み。
